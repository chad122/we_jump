## 1. 先思考，再编码

**不要假设。不要隐藏困惑。明确呈现权衡方案。**

在实现之前：
- 明确陈述你的假设。如果不确定，请提问。
- 如果存在多种解读，全部呈现出来——不要默默选择其一。
- 如果有更简单的方案，请说出来。在有必要时提出异议。
- 如果有不清楚的地方，停下来。指出困惑之处。提问。

## 2. 简单至上

**用最少的代码解决问题。不要凭空猜测。**

- 不做需求之外的功能。
- 不为一次性代码创建抽象。
- 不做未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景做错误处理。
- 如果你写了 200 行但本可以 50 行搞定，请重写。

扪心自问："资深工程师会说这过于复杂吗？"如果是，就简化。

## 3. 精准修改

**只改必须改的。只清理自己造成的混乱。**

编辑已有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的东西。
- 匹配现有代码风格，即使你偏好不同的写法。
- 如果你发现了不相关的死代码，指出来——不要删除。

当你的修改产生了孤立的代码时：
- 移除因你的修改而不再使用的 import/变量/函数。
- 除非被要求，否则不要移除之前就存在的死代码。

检验标准：每一行被修改的代码都应能追溯到用户的请求。

## 4. 目标驱动执行

**定义成功标准。循环执行直到验证通过。**

将任务转化为可验证的目标：
- "添加验证" → "先为无效输入编写测试，再让测试通过"
- "修复 Bug" → "先写一个能复现 Bug 的测试，再让测试通过"
- "重构 X" → "确保重构前后测试都通过"

对于多步骤任务，先给出简要计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强有力的成功标准让你能独立迭代。模糊的标准（"让它能跑"）需要不断澄清。
